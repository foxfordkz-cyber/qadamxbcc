# Проверяемые ML-результаты Saq Bol

## Сравнение порогов в закрытой панели SOC

При закрытии дела сотрудник выбирает исход расследования. После повторного открытия дела прежняя метка исключается из расчёта.

В кабинете сотрудника откройте «Аналитика» → «Пороги риска». В закрытой панели сайта сравнение доступно в разделе дел SOC. Сервер берёт до 100 последних переводов, в кошельке — за выбранные 7, 30 или 90 дней. Сравнение использует сохранённое исходное решение по каждому переводу. Все пробные политики сохраняют исходные блокировки и паузы. На ранее одобренный перевод добавляется пауза, если его исходная оценка достигла порога 25, 30, 35 или 40.

Таблица показывает дополнительные паузы по всей оценённой выборке и пропуски среди переводов с подтверждённым мошенничеством. Ложные паузы на 1 000 законных вычисляются как 1 000 × число вмешательств среди подтверждённых законных переводов / число подтверждённых законных переводов. Охват разметки — доля оценённых операций с однозначным установленным исходом. Прочерк в метрике означает отсутствие подходящих наблюдений. Для появления метки сотрудник закрывает дело по оценённому переводу с исходом «Мошенничество подтверждено» или «Законный перевод». Измерения HTTP в административном кабинете агрегированы по времени, поэтому p95 для конкретной выборки сравнения недоступен.

Это проверка синтетического прототипа, не измерение качества на клиентах банка.
На первом слайде не следует писать «точность 98%»: генератор данных и модель имеют
общие предположения, а выборка не является временным или клиентским holdout.

## Версия v3 и переводы под диктовку

При активном звонке v3 применяет лес, обученный на 18 000 синтетических переводов.
Среди них есть перевод знакомому получателю под диктовку, обычный звонок родственнику,
медленный аккуратный ввод и платёж без телеметрии. Эти ситуации пересекаются по сумме и ритму
ввода. Для переводов без звонка сборка воспроизводит лес v2. В парной выборке из 10 000
операций все 8 296 оценок без звонка совпали с v2. Версия модели сохраняется с решением
по переводу. [Исходные измерения и SHA-256 обеих моделей](evidence/model-v3-paired.json)

Отдельный генератор формирует 640 переводов во время звонка знакомому получателю.
Обе версии получают одинаковые операции. Каждая проходит через полный движок с чистыми
Redis и графом в памяти. У 20% наблюдений генератор отключает телеметрию ввода.
Порог вмешательства равен 40. Все вмешательства здесь были временными паузами.

- Из 256 синтетических случаев принуждения v2 задержала 130, v3 задержала 168.
  Доля выросла с 50,8% до 65,6%. У v3 осталось 88 пропусков.
- Из 384 законных переводов v2 задержала 116, v3 задержала 123. При осторожном вводе
  число ложных пауз снизилось с 52 до 42 из 128. При обычном разговоре обе версии
  одобрили все 128 операций.
- Другая группа содержит пары с одинаковыми наблюдениями и разными намерениями.
  Из 128 законных операций этой группы v2 задержала 64, v3 задержала 81. Для пилота
  банку потребуется оценить цену лишней паузы и собрать подтверждённые исходы.
- На исходной смеси из 10 000 переводов при иллюстративном пороге сырой модели 50
  число найденных случаев снизилось с 2 305 до 2 291 из 2 372. Число ложных
  тревог снизилось со 109 до 105 из 7 628. Состав потока влияет на итог.
- На 700 прогретых оценках p95 модели с объяснениями составил 0,294 мс,
  p95 движка с fakeredis и графом составил 3,788 мс. HTTP, удалённый Redis,
  SQL и холодный старт измеряются отдельно. Артефакт этой сборки занимает 314 300 байт.

Модель и частоты стресс-сценариев опираются на синтетические предположения. Для
оценки на клиентах нужен согласованный с банком теневой прогон на разделённых по
времени данных и разбор ложных удержаний. [Парный отчёт](evidence/model-v3-paired.json)

Для воспроизведения создайте сборку v2 из коммита `fba823a` с его `uv.lock`,
запустите в её каталоге `backend` команду `uv run python -m scripts.train_fraud_model --output <путь-к-v2.joblib>`.
В каталоге `backend` текущей версии выполните

```sh
uv sync --frozen
uv run python -m scripts.train_fraud_model
uv run python -m scripts.compare_phone_coercion --baseline-artifact <путь-к-v2.joblib> --output ../.local-checks/model-v3-paired.json
uv run python -m scripts.benchmark_antifraud --samples 700
```

## Архив измерений v1 и v2

Следующие замеры и команды относятся к соответствующим историческим версиям.

Из `backend/`, после `uv sync --frozen` и подготовки доверенного artifact:

```bash
uv run python -m scripts.train_fraud_model
uv run python -m scripts.evaluate_fraud_model --output ../.local-checks/model-evaluation.json
uv run python -m scripts.evaluate_fraud_model --seed 20270119 --output ../.local-checks/model-evaluation-unseen-seed.json
```

Evaluator не обучает и не изменяет artifact. Сценарии используют отдельные экземпляры
fakeredis и графа, не обращаются к preview API и не меняют историю демонстрации.
JSON содержит SHA-256 artifact, версии модели/генератора/sklearn, seed, знаменатели
метрик, confusion matrix, интервалы FPR, исходы всех сценариев и ограничения.
Время исполнения evaluator не является benchmark задержки скорера.

Сохранённые JSON-снимки: [исходная v1](evidence/model-evaluation-v1.json),
[v2 и сравнение на одинаковых строках](evidence/model-evaluation-v2.json),
[новый seed](evidence/model-evaluation-v2-unseen-seed.json). Это результаты данного
прогона, а не динамические показатели работающего банка.

Для сравнения с сохранённым **доверенным локальным** artifact v1:

```bash
uv run python -m scripts.evaluate_fraud_model --baseline-artifact ../.local-checks/model-v1.joblib --output ../.local-checks/model-evaluation-v2.json
```

Joblib использует pickle; evaluator не скачивает модели. Старый binary игнорируется
Git, а исходный код v1 сохранён в истории репозитория. При отсутствии baseline-файла
обычная оценка v2 остаётся полностью воспроизводимой.

## Исправление подтверждённой ошибки распределения

В репетиции нормального перевода v1 выдавала ML-score **97,22**, хотя итоговое решение
оставалось `approved`, risk **14**. У получателя был один входящий контрагент и старая
история обычных расходов: входящий объём 123 000 ₸, исходящий 298 300 ₸, отношение
**2,425**. В последних settled-окнах не было быстрого вывода. Признак `transit_ratio`
давал около **+87,99** пунктов модельного score.

Причина: serving-признак — накопленное отношение исходящего к входящему объёму,
но синтетическая обучающая выборка почти все высокие отношения связывала с дропперами.
Обычные взаимные переводы и расходование средств не были нормально представлены.

В `bcc-synthetic-rf-v2` исправлен генератор: часть обычных счетов имеет отношение
0,25–3,0; часть законных сборов также имеет последующие выплаты. Доли смеси 45% и 10%
— явно заданные предположения симуляции, не статистика Казахстана. Лес, seed обучения,
пороги и правила итогового решения не изменены. На контрольном векторе этого
обычного счёта новый raw ML-score — **0,055**, а контроль с 13 отправителями и
транзитом 0,92 сохраняет высокий score **79,59**.

## Оценка на одинаковых данных

Зафиксированный cutoff raw ML = 50. Эти числа не являются результатом полного
гибридного решения: в продукте score модели добавляет максимум 15 пунктов к правилам.

| Выборка | Модель | TP | FP | FN | TN | Precision | Recall | FPR |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Seed 20261117, генератор v2, 10 000 строк | v1 | 2364 | 2533 | 46 | 5057 | 48,27% | 98,09% | 33,37% |
| Те же строки | v2 | 2346 | 101 | 64 | 7489 | 95,87% | 97,34% | 1,33% |
| Новый seed 20270119, 10 000 строк | v1 | 2356 | 2540 | 40 | 5064 | 48,12% | 98,33% | 33,40% |
| Те же новые строки | v2 | 2331 | 93 | 65 | 7511 | 96,16% | 97,29% | 1,22% |

Во второй выборке 2396 положительных и 7604 отрицательных синтетических метки.
95%-интервал FPR v2 составляет примерно **1,00–1,50%** только для этой симуляции.
Уменьшение ложных срабатываний сопровождается некоторым снижением recall; это не
следует скрывать. Новый seed снижает повторное использование случайных примеров,
но не устраняет общий с обучением генератор и не доказывает перенос на банк.

На старом генераторе v1 имела FPR 0,66%. Резкое ухудшение при добавлении законных
высоких оборотов показывает, почему высокий synthetic AUC сам по себе недостаточен.
Сохранён исходный отчёт v1; его нельзя напрямую сравнивать с v2 на другой выборке.

## Сценарная проверка полного движка

Исходная панель в сохранённых v1/v2-снимках содержит 10 случаев. На 20 ноября
панель расширена до **12**: добавлены попытка смены получателя при активном
удержании и законный перевод с точно такими же наблюдаемыми признаками.
[Новый полный результат](evidence/model-evaluation-20261120.json) сохранён отдельно;
старые снимки не перезаписаны. Это приёмочные случаи, а не выборка банковского потока:
обычный P2P, вставка без давления, обычный звонок, семейный планшет, сбор с 12
отправителей, законный тревожный перевод, телефонное принуждение, слабые признаки
принуждения, контекст захвата аккаунта и подтверждённый дроп-транзит.

- Пять обычных сценариев проходят. Семейное устройство и fan-in без вывода сами
  по себе не становятся доказательством дроп-схемы.
- Депозитный scam удерживается; подтверждённый дроп-транзит блокируется с risk 100.
- Законный тревожный контроль имеет те же наблюдаемые признаки, что и scam, поэтому
  тоже получает hold. Это **ложное ограничение**, а не доказанное мошенничество.
- Слабый сценарий «звонок + сумма 4× + долгие паузы» остаётся `approved`, risk **38**:
  ожидаемое удержание не достигнуто. Новая панель имеет **11/12 совпадений с ожидаемой политикой**
  (в исходной было **9/10**).
  Этот пропуск сохранён в отчёте; порог не подгонялся под него.
- В этой маленькой панели отключение ML не меняет статусы. Нельзя выдавать её за
  доказательство роста recall благодаря ML.
- На пороге вмешательства 40 новая панель даёт TP=4, FP=2, FN=1, TN=5.
  Второй ложный hold — намеренно сохранённый законный повтор во время проверки.
  Серверное удержание защищает от обхода паузы, но не умеет доказать намерение
  клиента. На пороге блокировки 75 TP=1, FP=0, FN=4, TN=7; удержания не считаются
  пропущенной защитой в интерпретации продуктовой политики, но остаются ниже
  этого отдельного числового порога. Такие малые знаменатели не дают банковский FPR.

## Что именно добавляет ML

Отдельная фиксированная сетка из **192 комбинаций** суммы, звонка, новизны, вставки,
пауз, ночного времени и устройства не содержит меток fraud. В ней ML изменяет
`approved` на `cooling_off` в **9 случаях**. Это проверка механизма, не метрика качества.

Например: сумма 4×, новый получатель и новое устройство дают rules/graph score **35**.
Модель v2 выдаёт **93,85**, добавляет **13** пунктов и переводит итог в **48 / cooling_off**.
Поведенческие признаки при этом не дают ML самостоятельно включить hard block.

Удаление браузерных измерений из того же замороженного леса на новом seed меняет
recall с 97,29% до 96,33%, но также немного меняет FPR. Это sensitivity check при
потере данных, не переобученная ablation и не доказательство причинного эффекта.

## Что нужно проверить в банке

Размеченная временная выборка с разделением клиентов, история подтверждённых потерь
и легитимных операций, сегменты торговых/личных счетов, корректное окно транзита,
calibration и prevalence, стоимость ложного hold, drift и пропуски сигналов.
До этого результаты можно использовать для проверки логики и объяснимости прототипа,
но не для обещаний процента предотвращённого ущерба или готовности к боевым платежам.
