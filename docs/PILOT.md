# Внутренний shadow-пилот Saq Bol

Технический профиль подготовлен для закрытого стенда с тестовыми или согласованными
обезличенными данными. Код не отправляет банковские платежи. Успешный запуск этого
профиля сам по себе не означает разрешение на обработку клиентских денег.

## Уже реализовано

- Изолированный compose, отдельные PostgreSQL/Redis volumes; БД и Redis не публикуют порты.
- PostgreSQL сохраняет стандартный synchronous commit; Redis использует AOF.
- Никакого автоматического seed, пресетов или генератора трафика.
- Два независимых service keys: transfer API и SOC/ready API. Проверка constant-time;
  слабые/пустые ключи, небезопасный CORS и demo overrides останавливают запуск backend.
- Закрытый интерфейс с отдельным логином/паролем для внутреннего оператора; CSRF origin
  check повторяется в API route. Ключи backend остаются на сервере Next.js.
- Обязательная настройка HTTPS public origin; frontend слушает только loopback,
  предполагается доверенный TLS gateway. Next.js route guard использует актуальную
  [конвенцию Proxy](https://nextjs.org/docs/app/api-reference/file-conventions/proxy).
- В пилоте время и новизна получателя определяются сервером. Клиентский `false` не
  подавляет вычисленный новый device. Биометрия остаётся недоверенным дополнительным сигналом.
- Сохранённые решения/причины/контекст, строгий hold, отмена и безопасный повтор запроса.
- Повторная проверка актуального сетевого риска перед выпуском hold; первоначальный ML-снимок
  сохраняется, результат повторной проверки записывается отдельно.
- Durable outbox для локального графа и Redis: запись создаётся в той же транзакции, что
  approved и ребро БД. Незавершённая доставка восстанавливается до следующей операции,
  чтения графа или успешного `/ready`; потеря Redis обнаруживается по epoch-маркеру.
- Неизвестный результат после сетевого сбоя сохраняет ID намерения. Endpoint
  `POST /api/v1/transfers/requests/{request_id}/abandon` возвращает уже выполненную
  операцию либо навсегда запрещает исполнение этого ID. Это не отзыв выполненного платежа.
- Ограниченные тела запросов, срок чтения тела и квоты запросов; ошибочная или неполная
  настройка защищённого frontend закрывает доступ, включая случай отсутствующего environment.
- Pilot требует заранее подготовленный совместимый ML artifact; повреждённая модель,
  NaN/Inf и несовместимая версия не заменяются автоматически обученной моделью.
- `/ready` проверяет БД, Redis и ML; `/health` показывает только liveness.

## Поднять стенд

Windows PowerShell из корня, указав настоящий адрес доверенного HTTPS gateway:

```powershell
.\scripts\configure-pilot.ps1 -PublicOrigin https://shield.bank.example
docker compose --env-file .env.pilot -f docker-compose.pilot.yml up -d --build --wait
```

Скрипт генерирует независимые случайные секреты в игнорируемом `.env.pilot`, не печатает
их и отказывается перезаписывать существующий файл. Секреты следует перенести в secret
manager банка. Для другого ОС создать такой же env-файл с шестью переменными из
`configure-pilot.ps1`; ключи/пароли должны быть независимыми криптографически случайными
строками (например, 32 random bytes в hex). Никаких `NEXT_PUBLIC_*` для секретов.

Gateway направляет согласованный origin на `127.0.0.1:3100`. Подключить корпоративный
SSO/MFA, rate limits и access logs на gateway; встроенный Basic Auth служит дополнительным
ограничением для закрытого стенда. Запуск оставляет базу пустой: согласованные аккаунты
и события нужно загрузить через банковский адаптер, а не через destructive seed.

Проверка после запуска: без credentials UI и API возвращают отказ; transfer key не
читает SOC; чужой Origin не отправляет POST; clean анкета не выпускает до срока;
повтор request_id не создаёт вторую операцию; перезапуск сохраняет ML/hold; выключение
Redis делает `/ready` неуспешным. Автотесты покрывают эти границы на уровне приложения.

## Что требуется от банка перед реальными данными и воздействием на платежи

| Условие допуска | Необходимый результат |
| --- | --- |
| Идентичность и полномочия | SSO/MFA, индивидуальные сотрудники/роли, клиентская сессия и проверка принадлежности sender_id. Service key не идентифицирует клиента. |
| Источники сигналов | Авторитетные device/session ID, депозитные события, банковская история, справочник получателей. Браузер не может подтвердить реальный звонок или вывод депозита. |
| Исполнение платежей | Bank adapter, резервирование/проводки, платёжный outbox, replay/reconciliation и действия при сбоях. Реализованный projection outbox восстанавливает граф/счётчики, но не проводки. Сейчас approved — событие симулятора. |
| ML-валидация | Размеченные данные, временной holdout, calibration, precision/recall и false-positive rate по сегментам; согласованные пороги и мониторинг drift. Синтетический score не калиброван. |
| Решения по hold | Утверждённые сроки, контакт банка, процедура независимой проверки и разграничение прав для раннего выпуска. В прототипе ранний выпуск отсутствует. |
| Аудит и приватность | Персональные operator IDs, неизменяемое хранилище аудита, retention, шифрование, маскирование и правила доступа/удаления, согласование службы безопасности. |
| Эксплуатация | Backup/restore drill, HA, нагрузочный тест по QPS/размеру графа, алерты и SLO. In-memory граф требует **одного backend worker**; несколько реплик без синхронизации недопустимы. |
| Приёмка | Shadow mode без влияния на деньги, сопоставление с решениями аналитиков, согласование запуска ответственными за fraud, операции и безопасность. |

До выполнения этих условий профиль предназначен для внутренней проверки. Не требуется
автоматически переносить британские, сингапурские или австралийские нормы в Казахстан;
локальные требования и политика банка согласуются отдельно.

## Известные технические пределы

Redis и PostgreSQL не являются одной транзакцией. Projection outbox обеспечивает повторяемую
доставку разрешённых событий в локальный граф и settled counters; startup/потеря Redis
восстанавливают последние 24 часа попыток и исполненных событий. Это операция восстановления,
для которой не заявляется задержка обычного скоринга. Граф хранится в памяти одного процесса.
История демо в Next-only режиме не персистентна. В пилоте этот режим отключён.

По умолчанию API принимает тело до 16 KiB за 10 секунд. Backend использует
`BCC_MAX_REQUEST_BYTES` и `BCC_REQUEST_RATE_LIMIT_PER_MINUTE` (120 по умолчанию),
ограничивая фактического сетевого peer. Frontend применяет отдельную общую квоту процесса
`BCC_REQUEST_RATE_LIMIT_PER_MINUTE` и предел тела 16 KiB. За reverse proxy клиенты делят
квоту; это защита небольшого внутреннего стенда, а не распределённый лимит на клиента.
Gateway должен применять собственные лимиты по аутентифицированному субъекту. `429`
возвращает `Retry-After`; повторять следует тот же request_id, а не создавать новую операцию.

Обычный скоринг поддерживает до 512 событий за 24 часа в каждом из восьми направлений
истории. При превышении возвращается `503`, без усечения истории и без разрешения
перевода; удержанный перевод остаётся удержанным. Граф ограничивает работу с одним
узлом 4096 смежными рёбрами/связями устройств, а разворачивание SOC-графа — бюджетом
16384 связей. Превышение также возвращает `503`. Повтор запроса не снимает эти пределы:
нужна обработка на стороне банка либо агрегатор для больших объёмов. Это намеренный
предел внутреннего стенда, а не готовность обслуживать банковский трафик.
Ограничение 512 задаёт конечный объём работы, а не гарантирует 15 ms на его границе.
Проверка восьми заполненных историй на локальном Redis показала превышение этого бюджета.
Для воспроизводимого замера использовать
`python -m scripts.benchmark_velocity_capacity --redis-url redis://localhost:6379/0`;
обычный `benchmark_antifraud` проверяет небольшие окна.
Перед банковским пилотом нужны серверные агрегаты и нагрузочная проверка на согласованной
инфраструктуре, включая время HTTP, SQL и восстановления, отдельно от времени скорера.

Отдельная проверка PostgreSQL запускается через `BCC_TEST_POSTGRES_URL` и
`python -m pytest tests/test_postgres_concurrency.py`. URL должен указывать на выделенный
тестовый сервер: тесты создают и удаляют только собственные случайные схемы `bcc_audit_*`.
Без URL эти проверки пропускаются; обычный oracle использует SQLite/fakeredis.

SOC feed показывает последнее ограниченное окно, а не полный журнал событий: `since`
не является надёжным курсором без потерь. Исправленные статусы видны при полном обновлении
окна. Для банковского аудита нужен отдельный журнал с устойчивым курсором и пагинацией.

Браузер хранит ID, состояние, время и SHA-256 отпечаток формы; сырые реквизиты, сумма и
биометрия не сохраняются. Отпечаток обеспечивает сопоставление повторной формы, но не
анонимизацию. Это состояние общей внутренней консоли: перед клиентским запуском требуется
привязка к аутентифицированному пользователю и политика выхода/очистки. API проверяет
роль сервиса, но не принадлежность sender_id конечному клиенту.

Не менять schema/модель на работающем стенде без миграционного окна и резервной копии.
