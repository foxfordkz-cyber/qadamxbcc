## 1. Публичная история — решение о безопасном переносе

Причина: `saq-bol-mobile` работает на Docker Free с временными SQLite/Redis. Dashboard действительно закрывает Shell и Disk, в действующем API нет полного экспорта. Остановка/новый запуск уже замечены в журнале, прежний UUID перестал находиться. Нельзя считать всю утраченную историю восстановимой из текущего контейнера. Обычная выгрузка списка переводов не является backup.

Права: владелец Render workspace и владелец целевой отдельной БД. Нужное действие: через Help → Support сервиса `srv-dc064iafngtc73b40ua0` уточнить, возможен ли приватный экспорт **уже работающей** файловой системы без замены процесса. Передать идентификатор сервиса и требование не запускать redeploy. Ответить на существование копии старого процесса может только провайдер; восстановление не гарантируется. Обращение автоматически не отправлялось.

Если провайдер предоставит доступ: выполнить существующий `python -m scripts.backup_mobile_sqlite <активный mobile.db> <закрытый snapshot>`, сохранить файл за пределами контейнера, проверить restore и hash. Секретные env и Redis переносить отдельно. При отсутствии такого доступа выбрать и явно согласовать план: сохранить нынешний сервис и дать **отдельную** PostgreSQL/Redis для staging, либо принять невозможность переноса утраченных записей и согласовать переход. Эта задача разрешением на потерю истории не является.

Риски: Deploy, Restart, смена тарифа/env/диска могут уничтожить текущий временный файл. Не выполнять их ради включения экспорта. Подготовлены CLI backup/import/restore, полная сверка и `render-staging-existing.yaml`. После независимого restore — заморозить запись/worker, снять окончательную копию, импортировать в пустую цель, сверить все строки/ID/балансы/связи и лишь затем согласовать cutover. Не разрешать двум стендам одновременно принимать операции. SQL backup не переносит Redis-сеансы автоматически.

## 2. GitHub Actions и review

Причина: annotations jobs содержат billing/spending-limit отказ. Это не ошибка assertion теста и не локальный PASS CI. Права: владелец биллинга аккаунта/организации `foxfordkz-cyber`, maintainer репозитория.

Открыть GitHub → Settings аккаунта-владельца → Billing and licensing → Budgets and alerts / Actions usage; устранить именно отображаемое ограничение или платёжную ошибку. Не повышать бюджет автоматически. Затем Repository → Actions → проверить workflows финального Draft PR → Re-run failed jobs. Сверить branch protection/required checks и провести review. Изменения #33 входят в #35; финальная ветка включает также #36. Проверять итоговый PR, не применять копии одинаковых патчей. Слияние в main — решение техлида, с сохранением авторства (обычный merge).

Подготовлены единая ветка, тесты и локальные evidence. После зелёного CI и review можно объединить исходники; публичный backend всё равно требует отдельного безопасного плана из пункта 1.

На проверенном main branch endpoint вернул `protected=false`, protection — 404,
rulesets — 403. Последнее не доказывает отсутствия правил организации; владелец должен
сверить их в панели. Никакие ограничения и проверки не отключались.

## 3. Live Guardian и непрерывная запись

Причина: публичный mobile настроен на `fake_enabled`; в нём нет актуального backend из интеграционной ветки. Read-only Telegram проверка подтвердила тестового бота `@bekzat_bcc_shield_test_bot` и отсутствие webhook, но новых сообщений и polling не было. Разрешение прошлой сессии истекло. Нужны стабильный общий PostgreSQL backend, ровно один poller/worker и новое согласие конкретного контакта на ограниченную сессию.

После пункта 1 настроить секреты только в приватном окружении: test mode, token, allowlist, стабильный signing key; API и worker должны видеть одну БД. Не подключать контакт без согласия, не запускать второй poller. Подготовленный `python -m app.integrations.telegram.hosted` использует PostgreSQL advisory lock; callback не распоряжается деньгами. Для теста двух подписей чат клиента и контакт должны различаться. Ранее подтверждён один личный чат — это не подтверждение второго участника.

Запись без монтажа, только синтетические средства:

1. Телефон 1: клиент, баланс; телефон 2: согласившийся контакт, подтверждённое приглашение. Ноутбук: mobile SOC, не jury room.
2. Клиент: учебный перевод 900 000 ₸ с признаком звонка (после проверки текущего preset). Показать UUID, сумму, серверную паузу и неизменённый баланс.
3. Контакт: получить уведомление, нажать ACK; дождаться сохранения события, затем «Есть подозрение», повторить кнопку один раз.
4. SOC: открыть **тот же UUID**, убедиться в одном деле и двух разных audit-переходах; выбрать разрешённый результат. Подозрение контакта не означает автоматического финансового решения.
5. Клиент: перечитать операцию, ответ сотрудника и квитанцию/PDF; показать тот же UUID и баланс. Подозрительный перевод должен оставаться удержанным либо быть явно отменён разрешённым действием.
6. Вернуться после фона/закрытия, сверить состояние и отсутствие второй операции/списания. Сохранить видео и время проверки без секретов/чужих чатов.

Физическую проверку Honor владелец отменил в этой сессии; второго телефона для записи нет. Скриншоты старой установки помечены историческими. USB/команды/адрес API не являются частью сценария жюри.
