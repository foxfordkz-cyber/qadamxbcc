# Перенос мобильного стенда с сохранением истории

**Проверено на синтетической копии.** Скрипт `python -m scripts.import_mobile_snapshot <путь-к-snapshot>` перенёс 237 строк из SQLite в отдельную PostgreSQL. Сверены все модельные таблицы и типизированные строки, включая различие между SQL NULL и JSON null. Повторный импорт в заполненную цель отклонён. Исходный файл открыт только для чтения. Для репетиции задайте `QADAM_IMPORT_DATABASE_URL` через приватное окружение и выполните Alembic upgrade head на пустой локальной PostgreSQL с именем `qadam_import_rehearsal`. Импорт берёт блокировки целевых таблиц в одной транзакции и откатывает запись при расхождении. Схемы с неподдерживаемыми счётчиками также отклоняются. Пароли сервиса, ключи подписи и Redis имеют отдельный жизненный цикл.

Публичный мобильный шлюз https://saq-bol-mobile.onrender.com сообщил ephemeral_store=true во всех трёх проверенных сессиях. В scripts/mobile_ephemeral.py SQLite и Redis запускаются в TemporaryDirectory. Новый процесс создаёт новый каталог и вызывает seed. Сессии хранятся в Redis. Три хэша демоаккаунтов задаются переменными BCC_MOBILE_CLIENT_HASH, BCC_MOBILE_ADMIN_HASH и BCC_MOBILE_PLATFORM_HASH. Согласия, аудит, заявки и переводы находятся в SQL. Шаблон deploy/render-persistent.yaml и backend/scripts/start-persistent.sh используют PostgreSQL, отдельный Redis и Alembic. Текущий тариф и доступ оператора к файловой системе требуют подтверждения в Render.

1. Зафиксировать точную ревизию образа, конфигурацию сервиса и владельца, имеющего доступ к БД уже работающего процесса. Самостоятельный redeploy ради добавления экспорта уничтожил бы доступ к старому временному каталогу.
2. Внутри работающей среды при доступном приватном административном доступе запустить `python -m scripts.backup_mobile_sqlite <путь-к-активной-БД> <новый-защищённый-файл>`. Запускать в закрытом каталоге, на Windows с персональным ACL. Утилита использует online backup SQLite, сравнивает все строки, схему, внешние ключи и восстанавливает ещё одну копию. Передать snapshot в закрытое хранилище за пределами контейнера. Сохранить конфигурацию идентификаторов, исходные хэши, ключ подписи и разрешения доставки отдельно в хранилище секретов. При наличии авторизованного доступа сохранить Redis RDB со сроками жизни и проверить его на отдельном экземпляре.
3. На закрытой копии прогнать Alembic и пробный импорт в пустую целевую БД. Сверить каждый ID, суммы с точностью валюты, ключи идемпотентности, обращения и связи. Ограничить фоновую доставку тестовым адаптером до проверки очереди. Для согласованного переноса заморозить новые записи и worker, снять окончательный snapshot и повторить сверку. SQL backup сам по себе не переносит Redis-сессии.
4. Переключать клиентов только после подтверждённых сверок. До переключения оставить старую среду доступной без записи. Если новая среда уже приняла запись, сначала перенести и проверить изменения, затем откатывать маршрутизацию. Два независимых писателя создают расходящуюся историю.
5. При отсутствии доступа к текущему файлу владелец может сохранить работающий сервис и предоставить отдельную среду для репетиции. Для перехода с потерей истории потребуется отдельное решение владельца.

Локальная репетиция `python -m scripts.rehearse_release_storage` из backend создаёт собственные одноразовые контейнеры PostgreSQL и Redis, использует только синтетические аккаунты и loopback. Проверяет три решения, повтор запроса, две перезагрузки API с сохранением сессий и полное восстановление pg_dump в отдельную базу. Фактический результат указан в FINAL_ACCEPTANCE_RU.md.
