# Резервное видео BCC Shield

Сценарий длится около 2 минут 55 секунд: три пресета, настоящий таймер удержания,
пять вопросов, сохранение ответов без раннего выпуска, отмена, SOC, граф и ML.
Язык переключается на экране. Видео без озвучки; отдельные SRT позволяют выбрать
казахские или русские субтитры и выступать поверх записи.

## Воспроизведение записи

Использовать отдельный локальный стенд с синтетическими счетами. Скрипт создаёт
переводы через настоящий `/api/v1/...`, сохраняет анкету и отменяет один перевод.
Он не перехватывает API и не ускоряет время. Текущая пользовательская история
не должна использоваться как база для записи.

```powershell
$env:BCC_WEB_PORT = '3217'
$env:BCC_BACKEND_PORT = '8217'
$env:BCC_POSTGRES_PORT = '5547'
$env:BCC_REDIS_PORT = '6397'
docker compose -p bcc-video-demo up -d --build
```

Выбрать свободные порты и новое имя Compose-проекта. Bootstrap заполняет только
пустую базу; существующие данные не удаляются. Проверить `/ready` backend перед
записью. Это профиль demo, а не профиль клиентского пилота.

Нужны Node.js, Playwright Core, его FFmpeg и Chromium/Chrome. На машине подготовки
использованы Playwright Core 1.64.1 и отдельный Chrome-контекст без пользовательского
профиля. Пакет можно установить в отдельную папку:

```powershell
npm install --prefix .local-checks/browser-tools --no-save playwright-core@1.64.1
.\.local-checks\browser-tools\node_modules\.bin\playwright-core.cmd install chromium ffmpeg
$env:PLAYWRIGHT_MODULE = (Resolve-Path .local-checks/browser-tools/node_modules/playwright-core).Path
# Если нужен установленный Chrome вместо браузера Playwright:
$env:CHROMIUM_EXECUTABLE = 'C:/Program Files/Google/Chrome/Application/chrome.exe'
node scripts/record-demo.mjs --url http://127.0.0.1:3217 --allow-demo-writes --output deliverables/demo
```

Скрипт принимает только явно указанный loopback URL и флаг разрешения демо-записей.
Он проверяет ответы `approved`, `cooling_off`, `blocked`, сохранение анкеты,
отсутствие раннего разрешения, отмену и отсутствие ошибок браузера/API.
При ошибке процесс возвращает ненулевой код. Публиковать следует только успешно
завершённую запись с соответствующим `manifest.json`.

Выход: `BCC-Shield-demo.webm` (1920×1080), `.ru.srt`, `.kk.srt`, пять контрольных
кадра и manifest с SHA-256, ID синтетических операций и измерениями API.
Полную длительность контейнера WebM нужно проверить отдельно: manifest содержит
длительность основного сценария и приблизительный начальный интервал загрузки.

## Как показывать

Сначала предпочтительно живое демо. При нестабильном интернете открыть WebM
в браузере или плеере; для субтитров загрузить одноимённый SRT нужного языка.
Файл не требует backend и подключения к банку. Для жюри объяснить, что это запись
работающего синтетического прототипа, а не реальные банковские платежи.

Показанный ML score не является доказательством мошенничества. p95 карточки SOC
относится к измерениям скорера и включает размер выборки; полная задержка HTTP/SQL
и банковская нагрузка требуют отдельного измерения в пилоте.

## Проверенная запись 18 ноября 2026

`deliverables/demo/BCC-Shield-demo.webm`: **2:54.76, 1920×1080, VP9, 25 fps**,
без аудио. Проверены метаданные контейнера и декодированный кадр; пять PNG
сняты в ходе записи. SHA-256 находится в `manifest.json` и `verification.json`.
Это живой FastAPI и production frontend на Windows-хосте с PostgreSQL/Redis
в отдельном Compose-проекте `bcc-video-20261118`. Начальная база содержала 299 синтетических счетов и 2514
операций; сценарий создаёт три операции и короткий синтетический поток. Пользовательская база с 137 операциями
не изменялась.

На записи получены `approved` → `cooling_off` → `blocked`; сохранение чистой анкеты
оставило удержание, отдельная отмена завершила второй перевод как `cancelled`.
Все проверки сценария прошли, ошибок API/JavaScript не было.
Прямой граф содержит 16 узлов, расширенный — 60. Короткий живой поток показывает
250 000 ₸ заблокированных переводов симуляции и затем явно останавливается.
Три основных оценки в окончательной записи заняли 3.332, 9.068 и 7.636 мс.
Это отдельные наблюдения, а не оценка p95. Субтитры выровнены по длительности
готового файла; проверено, что все пять ML-вкладов попадают в записываемый кадр.

Производительность опубликована без выборочного удаления неудачных замеров:
[машиночитаемый отчёт](evidence/role-performance.json). На 500 прогретых оценках
с настоящим Redis p95 скорера составил **9.59 мс на Windows-хосте** и **15.88 мс
в общей Docker VM** с 2 CPU; p95 ML — 0.25 и 0.45 мс соответственно. Цель 15 мс
в этом Docker-прогоне не достигнута. В предыдущей Docker-записи отдельные оценки заняли
41.82–54.14 мс. Ранний замер параллельно
экспорту образа завершился таймаутом Redis. Это стендовые наблюдения, не подтверждение
банковского SLO. Следующая проверка производительности требует выделенных ресурсов,
полного API-пути и согласованной конкурентной нагрузки.

При повторной записи на Docker backend был получен 502: запрос завершился на
сервере позднее. Повтор с исходным UUID вернул одно уже сохранённое решение
`approved`; дубликат не создавался. Устойчивость к неизвестному исходу нужна и
в демо. Для финального видео FastAPI перенесён на хост, алгоритмы не менялись.
В расширенном графе сохранены все возвращённые API узлы; начальный вид показывает
16 счетов и 16 связей с явным переключателем глубины.
