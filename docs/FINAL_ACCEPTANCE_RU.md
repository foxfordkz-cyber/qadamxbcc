# Qadam Shield 2.9 — приёмка учебной сборки

22 ноября 2026 г. Ветка `feature/final-demo-release-readiness`, [draft PR #28](https://github.com/foxfordkz-cyber/qadamxbcc/pull/28). За основу взята принятая мобильная ветка `ab1f970` и изменения командного сайта из `4f124d0` с последующей интеграцией командного брендинга и связанного SOC из `c654fbb`. Исходники UI внутри APK соответствуют `815b90226f82f54ea49115f134a010c91203b7eb`. После проверки на Android 11 убраны зависимости от top-level await и нескольких новых JS API. Учебные переводы по-прежнему используют криптографические ключи идемпотентности. Базовая 2.8 уже имела ролевой вход, операции, Trusted Circle, обращение с ответом оператора, аналитику и граф.

## Проверки и воспроизведение

- Android: `npm ci`, Capacitor sync, Gradle `assembleShowcase assembleDebug` под JDK 21. Последняя локальная сборка заняла 1 мин 31 с. Модули UI — 44 проходящих теста.
- Frontend: 187 тестов, сборка Cloudflare и smoke в workerd с ответом APK, проверкой SHA и маршрутов.
- В полном CI на `bad75c2`, до последней правки обработки callback Guardian, прошли **778 уникальных backend-тестов**, 3 остались пропущенными. Подсчёт выполнен по идентификаторам тестов в JUnit из заданий с разными сервисами. В прежней локальной выборке `tests/test_mobile_gateway.py tests/integrations` прошли 359, пропущены 15. Эти числа пересекаются. Отдельно проверены приватность пакета и резервная копия SQLite.
- После изменений на Windows подтверждены 754 уникальных backend-теста. 29 пропущены в этом окружении. В первом полном запуске один тест увидел второе SOC-дело до появления результата MOCK. После исправления ожидания прошли сценарий подготовки дел и все пять целевых регрессий. Числа пересекаются с предыдущими CI-прогонами. Ruff прошёл, mypy проверил 131 файл.
- Финальный клиент проверен в Chrome через Playwright. Прошли 32 сценария, 3 отдельных сценария с внешними стендами пропущены в этом запуске. Среди пройденных — вход после сбоя, защита от повторной отправки, RU/ҚАЗ и переходы между операцией и обращением. Для интеграционных сценариев с PostgreSQL и тремя ролями отдельно приведены результаты репетиции и предыдущего CI.
- PostgreSQL и Redis: `python -m scripts.rehearse_release_storage` в каталоге backend требует Docker Desktop. Репетиция создаёт собственные базы и временные учётные данные, переносит pg_dump за пределы контейнера и проверяет восстановление.
- Публичный сервис, Telegram и основная база команды в репетиции хранения не участвуют. Перенос хэшей и внешних переменных, TTL Redis и работа реальной очереди требуют доступа оператора.

## Проверка на устройствах

На физическом Honor VNE-LX1 сервер принял клиентский вход. Package Manager подтвердил `kz.qadamx.bccshield.demo`, `versionCode=15`, `versionName=2.9`. Последняя установка завершилась командой `adb install -r`. Сохранённая сессия открыла клиентский кабинет после остановки и повторного запуска Activity. Для кода 14 главная появилась в дереве интерфейса через 17 243 мс, включая интервалы опроса. Запуск Activity кода 14 занял 1695 мс. После установки кода 15 на Honor холодный запуск Activity занял 3781 мс. Все значения получены в отдельных одиночных наблюдениях. Пароли при проверке использовались только на хосте.

На чистом AOSP Android 11 (API 30) сначала проверено отсутствие пакета. Системный установщик вернул `Success`, SHA-256 установленного `base.apk` совпал с манифестом 2.9 (15). На WebView 83.0.4103.120 открылась форма входа с двумя полями. В предыдущем локальном профиле API 37.1 код 13 установился, для кода 14 там прервалась связь с Package Manager. В PR добавлена [проверка для чистого Android 30](../.github/workflows/showcase-install.yml). На физическом Honor проверены три входа. Сотрудник открыл список дел SOC, platform — экран доступа сотрудников. После завершения проверки снова открыт клиентский кабинет.

## Приёмка Telegram Guardian

Владелец заранее подтвердил личный чат и дал отдельное разрешение на 15 минут и три сообщения. Перед отправкой проверены имя и идентификатор бота, отсутствие webhook и локальная блокировка polling. Реальный Bot API принял приглашение, запрос согласия и одно уведомление Guardian. Обработчик aiogram получил согласие. Синтетический перевод на 900 000 ₸ в изолированном мобильном API получил Cooling-Off. Worker записал подтверждение отправки. После нажатия в Telegram новый запрос к клиентскому API прочитал `SUSPICION_REPORTED`. В этом тесте SQL находился в памяти, для вспомогательных Redis-операций использовался fakeredis.

Пользователь сообщил об обоих нажатиях. Проверка отдельно наблюдала только итог подозрения. В обработчике этой версии нажатие «Есть подозрение» скрывало обе кнопки. После приёмки изменены журналирование позднего ACK и клавиатура. Подозрение остаётся текущим статусом, а получение можно зарегистрировать вторым событием. Новая реальная отправка после изменения обработчика не выполнялась.

### Сопоставление двух версий интерфейса

Измерение интерфейса перед исправлением совместимости с WebView 83. Одинаковые Chrome, ширина 390 px и публичный HTTPS API. HTML/CSS/JS брались из исходников каждой версии. На одном проходе 2.8 → 2.9 форма входа появилась за 632 → 297 мс, вход до видимого баланса занял 1562 → 1138 мс, восстановление баланса после reload — 1137 → 941 мс, открытие квитанции — 592 → 634 мс. Это единичные браузерные наблюдения. Для оценки устойчивого изменения скорости нужны повторения.

Для 2.8 и кандидата 2.9 отдельно выполнен одинаковый синтетический сценарий через HTTPX ASGITransport, SQLite в памяти и fakeredis. Время от отправки запроса до получения ответа для деталей SOC-дела составило 52,9 → 56,4 мс, чтения доказательств — 53,3 → 72,8 мс, ответа на отмену владельцем — 92,5 → 87,1 мс. По одному наблюдению на ревизию. Измерения исключают мобильную сеть и отрисовку Android.
