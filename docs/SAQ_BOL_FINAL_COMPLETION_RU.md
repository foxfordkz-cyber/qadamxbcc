## Публичное хранение

Render Dashboard показал действующий коммит `2ffc009ee7a9cd9b5b7b0711a7deb7aeeb3bc2a5`, регион Oregon и тариф Free для `saq-bol-mobile`. В его исходниках `scripts/mobile_ephemeral.py` при старте создаёт SQLite `mobile.db` внутри `TemporaryDirectory(prefix="saq-mobile-")` и отдельный процесс Redis с Unix-сокетом в том же каталоге. Три авторизованных чтения публичного мобильного API вернули HTTP 200 и `ephemeral_store=true`. Публичная сессия, ledger, операции, обращения, согласия и аудит подвержены потере при пересоздании среды. Хэши демопаролей настроены отдельно от временной SQL-базы.

В рабочей области видны отдельные `saq-bol-api-db` (PostgreSQL 18) и `saq-bol-api-cache` (Valkey 8) для основного API. Наличие этих ресурсов само по себе не даёт мобильному сервису отдельную согласованную базу или право менять схемы команды. В панели Shell для мобильного сервиса Render прямо требует платный compute. Текущего приватного снимка публичных SQL и Redis нет. Инструкция по резервной копии, тестированию восстановления и откату — в [PERSISTENCE_AND_RECOVERY_RU.md](PERSISTENCE_AND_RECOVERY_RU.md).

### Новое дело на изолированном стенде

На том же Redmi отдельно установлен отладочный APK с origin, закреплённым за локальным учебным API. Установленные байты сверены с SHA-256 отладочной сборки. Телефон отправил запрос перевода на 900 000 ₸ с отметкой о давлении в звонке. На экране появилась нейтральная надпись об обработке. Для продолжения проверки серверный журнал прочитан по клиентской сессии, существующий перевод найден без повторной отправки.

Из квитанции на телефоне создано новое обращение. Сотрудник открыл связанное дело в браузере, прочитал три группы факторов, назначил дело на себя и внёс заключение «Мошенничество подтверждено». На том же Redmi клиент открыл уведомление о закрытии дела. В резолюции проверены номер дела, сумма и результат. Мобильный API подтвердил совпадение идентификатора и суммы операции, финансовый статус остался `cooling_off`. Все действия относились к локальным синтетическим данным.

### Восстановление постоянного стенда

На двух новых контейнерах PostgreSQL 16 и Redis 7 прошли миграции и тесты импорта. Репетиция выполнила три синтетических перевода с решениями approved, cooling_off и blocked, затем отменила удержанный перевод по ответу клиента. После двух остановок и запусков процесса API сохранились три сессии, баланс и история. Повтор исходного запроса вернул прежний transaction ID. Полный `pg_dump -Fc` восстановлен в отдельную БД и сверен с оригиналом по каталогу схемы и фактическим строкам каждой таблицы. Этот backup относится к локальной репетиции. Публичный Render продолжал работать без перезапуска.
