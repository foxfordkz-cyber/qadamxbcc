# Проверка восстановления переводов — 18 ноября 2026

Рабочая ветка: `codex/tanirbergen-recovery-20261117`, исходный `main`: `e3e544f`.
Продолжен существующий BCC Shield. Все операции и данные в проверках синтетические.

## Область работы

Исправления охватывают восстановление сохранённых переводов, сохранение выбора
оператора при фоновых ответах и точность сетевых признаков в SOC. Исходные
пороговые значения и веса скоринга сохраняются. Отдельные мобильная и
интеграционные ветки команды не переносились.

## DONE

- Сохранённое решение можно прочитать, удержание отменить, а неопределённое
  намерение запретить к исполнению при сбое Redis или доставки другой проекции.
  SQL-блокировки, проверка прав, идемпотентность и единственная запись отмены
  сохраняются. Новый скоринг и выпуск удержания требуют рабочих зависимостей.
- Фоновое восстановление B не подменяет выбранный перевод A. Изменённая форма
  остаётся без старой квитанции; потерянный ответ по-прежнему восстанавливается.
  Неудачный просмотр A очищает ранее показанную чужую квитанцию B.
- Счётчик уникальных заблокированных хабов учитывает явные `RECHECK_*` причины
  повторной проверки. Обычные scam-блокировки не считаются хабами.
- Демонстрационный граф каждого из четырёх счетов имеет уникальные узлы без
  искусственной петли на центральном счёте.
- Смена или очистка зарегистрированного устройства удаляет прежнюю регистрацию
  из графа, сохраняя независимые наблюдения demo и явные shared-device связи.
  До оценки и выпуска удержания обновляются актуальные составы затронутых
  устройств, включая ранее известных соседей, которые сменили устройство.
  Неизвестное пустое устройство не образует группу. Превышение лимита группы
  отклоняется до финансовых записей; неподтверждённое устройство не привязывается
  к отправителю в pilot.
- Переносимый `npm run test:recovery-ui` проверяет шесть сценариев восстановления
  на локальном синтетическом demo; live/pilot и внешние адреса отклоняются.
- Три ранее зависевших от часа суток сценария получили явное дневное время.
  В двух сетевых сценариях согласованы часы попыток, фактического исполнения,
  повторной проверки и восстановления. Ночные правила и их тесты не менялись.

не разделяли временные каталоги. Из `frontend/` выполнены `npm run typecheck`,
`npm test`, `npm run build`, `npm run test:recovery-ui` и `npm audit --omit=dev`.
Подготовка браузерного сервера описана в README. Единый `verify.ps1` целиком не
запускался; перечисленные проверки выполнялись отдельными командами.

При физически остановленном Redis сохранённые чтение/отмена/abandon вернули
успех; `/ready` — 503, новая evaluate и выпуск удержания — 500. Для двух последних
проверено отсутствие исполнения и изменения SQL. После возврата Redis состояние
отмены и запрет позднего исполнения сохранились, повторная отмена не добавила
второй аудит, граф/settled counters не получили сумму отменённого перевода.

## История обнаруженных отказов

- До исправления оба frontend-теста SOC evidence падали: хаб после recheck не
  считался, граф обычного счёта содержал повторный ID.
- До исправления backend-пример с `RECHECK_` возвращал 0 хабов вместо 1.
- Первые проверки обновления устройств: 6 FAIL, 2 PASS. Они воспроизвели
  устаревшие регистрации, неполные сведения перед выпуском и отсутствие
  отклонения слишком большой группы. В итоговом наборе все 11 новых тестов PASS.
- Первый полный серверный прогон: 185 PASS, 3 FAIL, 3 SKIP. Причиной трёх отказов
  был реальный ночной час: cashout получил 75 вместо 65 баллов, обычный перевод —
  10 вместо 0. Исправлены часы тестов, а не веса или пороги продукта.
- pytest 9.2 отверг относительный `cache_dir` с `..` до запуска тестов; абсолютные
  пути устранили ошибку настройки.
- Первый браузерный запуск ожидал неверный русский текст; исправлено ожидание
  теста, после этого все сценарии прошли.
- Первый порт PostgreSQL попал в запрещённый Windows диапазон. Выделенный
  loopback-порт 18432 запустился успешно; чужие службы и volumes не удалялись.
- `npm audit` с dev dependencies сообщает 10 HIGH через цепочку Tailwind 3 /
  picomatch. Автоматический предложенный переход на Tailwind 4 не применён;
  production dependency audit отдельно возвращает 0. Это не полный security audit.

## NOT TESTED / внешние границы

Холодный запуск приложения при недоступном Redis по-прежнему требует зависимости.
Реальная fault-проверка запускалась на отдельной схеме, созданной из SQLAlchemy
metadata: она не доказывает PostgreSQL migration upgrade. Использован PostgreSQL
17, а основной compose репозитория указывает 16. Настоящие деньги, банковское ядро,
Telegram, внешние интеграционные ветки, production, HA и нагрузочный SLA не
проверялись. Чужие PR не сливались.

Обновление составов устройств не делает внешние параллельные изменения Account
атомарными со скорингом. Полная непрерывная синхронизация исторических устройств
и вновь добавленных явных shared-device связей не реализована этой правкой.
Поведенческие пороги, веса правил и банковские acceptance gates не менялись.
