# Учебный набор wallet-v1

Набор дополняет синтетическую базу только в отдельном Compose-проекте `qadam-handoff`. PostgreSQL `qadam_handoff`, отдельный Redis, кошелёк на порту 18127 и каталог локальных паролей отделены от мобильного Render, jury и общей базы команды. Штатный bootstrap инициализирует пустую базу. Не вызывайте scripts.seed_bcc на существующей базе: его внутренний _clear очищает данные.

## Подготовка из корня на Windows

```powershell
npm.cmd --prefix android-app ci
npm.cmd --prefix android-app run web
$compose = @('-p','qadam-handoff','-f','docker-compose.android.yml','-f','deploy/compose.handoff.yml')
docker compose @compose up -d --build --wait
docker compose @compose exec -T gateway python -m scripts.handoff_data
docker compose @compose exec -T gateway python -m scripts.handoff_data --apply
docker compose @compose exec -T gateway python -m scripts.handoff_data --apply
```

Откройте `http://127.0.0.1:18127/wallet/`. Локальные роли client_demo, admin_demo и platform_demo используют поля client, admin и platform_admin из `.local-checks/handoff-access/access.json`. Для остановки используйте `docker compose @compose stop`. Сохраните тома PostgreSQL и Redis и локальный файл доступа.

Предпросмотр выполняет импорт в откатываемой транзакции и выводит фактические исходные количества и денежный эффект по каждому из 13 счетов. Применение фиксирует транзакцию целиком. PostgreSQL advisory lock сериализует параллельные импорты. Идентификаторы переводов и ключи создания обращений зависят от версии набора. Первая операция отмечает применённую версию. При повторном запуске импорт возвращает added=0 и сохраняет изменённые дела, контакты и ответы. Даты исторических операций фиксируются при первом применении. У обращений действуют штатные сроки хранения. Повтор импорта не продлевает их искусственно.

## Контроль после подготовки

В корне репозитория с поднятым локальным стендом выполните:

```powershell
docker compose @compose exec -T gateway python -m scripts.check_handoff_data
node android-app/scripts/check-handoff.mjs
```

Первую команду можно выполнить сразу после запуска пустого стенда. Она снимет контрольную выборку, проверит откат предпросмотра, применит набор и повторит импорт. Проверяются все прежние операции и остатки, отсутствие новых заданий доставки, соответствие владельцев обращений отправителям и неизменность версий дел и событий при повторе. Вторая команда использует установленный Chrome и три отдельные сессии на loopback. Она отмечает одно учебное обращение от лица SOC, сверяет результат у клиента и сохраняет снимки экранов в `docs/handoff-evidence/`.

На чистом локальном PostgreSQL штатная подготовка создала 299 счетов и 2 514 операций до применения `wallet-v1`. Эти количества относятся ко всей базе. Число видимых клиенту строк дополнительно зависит от принадлежности счёту, статуса и выбранного периода.

## Что показать

Добавляются 20 пар встречных учебных операций в ₸ за 86 дней, 12 существующих контрагентов, 10 связанных обращений и дел. Четыре обращения принадлежат клиенту и шесть — другим отправителям. Суммы встречных проводок равны для каждого счёта. Граф получает суммы, количество и дату реальных для этой учебной базы проводок. Штатный seed отдельно создаёт сеть дроп-хаба и фоновые операции. Возможные состояния дел включают NEW, IN_REVIEW, NEEDS_INFORMATION, ESCALATED и CLOSED; история содержит назначения и заметки. Подготовлен запрос информации с ответом клиента.

До трёх синтетических контактов обозначены словом «Демо», с выключенной доставкой, без Telegram chat ID и токенов. Набор не создаёт сообщений в outbox. Шлюз запускается с fake-адаптером. Уведомления в интерфейсе выводятся из записей операций, контактов и обращений. Штатная модель не хранит флаг прочтения каждой строки.

| Экран и действие | Источник | Публичная проверка до импорта / заполненная репетиция |
|---|---|---|
| Главная → карта, история | /account, /wallet/operations | Уже есть баланс и 12 операций / плюс 40 согласованных проводок |
| Перевод → выбрать получателя | /account.recipients, /api/transfers/evaluate | Три штатных получателя и четыре контрагента из добавленных исходящих операций. В истории доступны подробности встречных переводов |
| История → квитанция | /wallet/operations, transfer detail или /wallet/incoming/{id} | Фильтры и страницы сохраняют область клиента |
| Аналитика → день | /wallet/analytics?days=7,30,90 | Сводка по тому же журналу и календарю Казахстана |
| Защита → круг, уведомления | контактные API, /inbox | Синтетические состояния и события с переходами в детали |
| Мои обращения → подробности | /api/integrations/guardian/reports | На мобильном сервере было 0 / четыре собственных обращения |
| SOC → дела, источник, комментарий | /wallet/cases, guardian/soc/cases | На мобильном сервере было 0 / десять дел с конкретной операцией |
| Граф → выбор участника или ребра | граф SOC, /wallet/graph-operations | Профиль участника в графе открывает его исходные операции |
| Платформа → нагрузка, доступ | /admin/metrics, /admin/staff | Реальные метрики запросов и текущее состояние сотрудника |

1. Клиент открывает выполненный перевод и квитанцию. В аналитике выбирает день и сверяет сумму. Для новой обычной операции используется `normal`, 25 000 ₸.
2. Для **новой** паузы выберите `scam`, 900 000 ₸, и подтвердите в интерфейсе. Решение и срок приходят с сервера в момент оценки. Guardian передаёт advisory-сигнал, отмену выполняет клиент. Учебный контакт не подтверждает платежи. Пресет `hub` показывает отдельно заблокированного получателя.
3. Откройте связанное обращение клиента. В другом профиле браузера SOC открывает дело с тем же report ID, квитанцию и историю. Для незакрытого дела выберите разрешённое действие, запросите информацию и ответьте из клиента. В платформенной роли покажите доступ SOC без изменения прав.

Серверный срок паузы и срок действия обращений продолжают идти после закрытия приложения. Старый набор может выйти из выбранного периода. Используйте историю и доступный диапазон дат. Общие демоданные не сбрасываются.
