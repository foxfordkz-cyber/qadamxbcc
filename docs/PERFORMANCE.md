# Saq Bol — производительность, 20 ноября 2026

## Замер после защиты от повторной попытки

На версии `656133e` p95 гибридного скоринга составил **5,00 мс** при целевом
бюджете **15 мс**. Отдельный вызов ML с объяснением занял **0,176 мс на p95**.
В микротесте ядра использовались реальные Redis, граф и модель. Полный путь
с проверкой активной паузы в SQL и сохранением результата измерялся через HTTP.
[Данные и версии кода](evidence/performance-active-hold-20261120.json).

| Ядро и Redis, один вызов | 500 | 3,78 | 5,00 | 5,46 | — |
| HTTP, 1 одновременный запрос | 500 | 67,17 | 98,86 | 157,10 | 14,6 |
| HTTP, 8 одновременных запросов | 500 | 281,99 | 505,58 | 605,44 | 28,1 |

На ноутбуке FastAPI/Uvicorn работал одним процессом. Docker сообщил **2 vCPU
и 3,83 ГиБ** для PostgreSQL 16.15 и Redis 7.4.12. В PostgreSQL включён
`synchronous_commit`. Для каждого из трёх измерений использовался отдельный прогрев
из 30 вызовов. Нагрузку подавали после завершения локальных сборок и браузерных
проверок. Порядок измерений и генератор трафика совпадают с описанием ниже.

Свежая база содержала 299 счетов и 2 514 операций. По завершении в ней было
**3 574 операции**. Все **1 060** HTTP-запросов с учётом прогрева завершились
без ошибок. В каждой измеренной выборке заблокированы 50 из 50 сценариев хаба
и удержаны 50 из 50 сценариев телефонного давления. Среди 400 обычных запросов
на удержание попали 11 при c1 и 81 при c8. История сохранялась между сериями.
Отдельный запрос к таблице причин после измерения показал **0 срабатываний
`ACTIVE_HOLD_RETRY`**. Общие HTTP-процентили включают поиск активной паузы.
Задержка ветви, которая фактически наследует срок паузы, требует отдельного замера.

HTTP p95 превышает 15 мс при обоих уровнях конкурентности. В исходном прогоне
до изменения паузы получены 55,24 и 274,38 мс соответственно. Квоты Docker
для того прогона не зафиксированы, поэтому стоимость самого изменения SQL
по разнице этих значений определить нельзя.

## Исходный замер до изменения серверной паузы

На версии `de601ce` p95 прогретого ядра составил **4,90 мс**, ML — **0,12 мс**.
Время HTTP-запроса с записью в PostgreSQL составило **55,24 мс** на p95 при одном
клиенте и **274,38 мс** при восьми. В двух выборках по 500 запросов и при прогреве

## Окружение и надёжность записи

- Windows 11 10.0.26200; Ryzen 5 7535HS, 6 ядер / 12 потоков; 15,25 GiB RAM.
- Python 3.12.14, один процесс Uvicorn на Windows, без дополнительных workers.
- PostgreSQL 16.15 и Redis 7.4.12 в отдельных контейнерах Docker Desktop 29.1.5.
- PostgreSQL: проверено `SHOW synchronous_commit = on`. Это также новый default
  `docker-compose.yml`; ради задержки подтверждение записи не отключается.
- Redis без дисковой персистентности на изолированном синтетическом стенде.
  Это не проверка восстановления после потери питания.
- Миграция `0009_recipient_flags`; свежий seed: 299 счетов, 2514 операций.
  Для HTTP используется пул из 200 фоновых счетов, отдельная база
  `bcc_performance_20261120`, а не база открытого демо.
- Только на стенде `BCC_REQUEST_RATE_LIMIT_PER_MINUTE=10000`; default остаётся 120.
- Во время измерений другие тесты и сборки не выполнялись. Engine, HTTP c1 и c8
  измерены последовательно. История между HTTP-прогонами сохранялась, поэтому
  накопленные сигналы и решения не обязаны совпадать.

## HTTP с PostgreSQL и Redis

Каждый запрос — новый UUID `request_id`, реальное решение и запись в БД. Трафик:
80% обычных переводов, 10% социальной инженерии, 10% на seeded dropper hub.
30 прогревочных запросов полностью завершаются до начала измеряемой фазы.

| Одновременных запросов | Выборка | p50, мс | p95, мс | p99, мс | max, мс | Ошибки | Запросов/с |
|---|---:|---:|---:|---:|---:|---:|---:|
| 1 | 500 | 45,08 | 55,24 | 93,49 | 213,68 | 0 | 22,4 |
| 8 | 500 | 194,38 | 274,38 | 397,51 | 451,98 | 0 | 43,3 |

Оба прогона: все 50 запросов хаба заблокированы; все 50 scam-запросов удержаны.
Обычных переводов одобрено 389 / 320, удержано 11 / 80: при повторении отправителей
накапливаются сигналы скорости. Это не оценка false-positive rate на размеченной
банковской выборке.

Методика — closed-loop: не более N запросов в работе, следующий запускается после
ответа. Ожидание в клиентской очереди не включено. Время включает получение и проверку
ответа на клиенте. Процентили используют inclusive linear interpolation; основная
выборка включает ошибки, success-only статистика сохранена отдельно. При отсутствии
успешных ответов её процентили равны `null`, не нулю. Проверяются полная схема ответа,
совпадение UUID и суммы; повреждённый HTTP 200 считается ошибкой. Любая ошибка,
включая прогрев, завершает CLI с ненулевым exit code.

Разница между engine и HTTP подтверждает затраты вне скоринга. Замеры не разделяют
цену SQL/WAL, Docker bridge, сериализации и конкуренции в одном процессе. Причину
нельзя приписать только одному фактору без профилирования. Для пилота нужны
согласованная банковская нагрузка и проверка надёжности хранения.

## Воспроизведение

Подготовить отдельные локальные PostgreSQL/Redis, свежую синтетическую БД, проверить
`SHOW synchronous_commit`, выполнить `alembic upgrade head` и `scripts.seed_bcc`.
Seed очищает демо-данные; в `pilot` он запрещён. Не использовать рабочую базу.
Запустить один Uvicorn с настройками выше. Команды из `backend/`:

```powershell
$env:PYTHONUTF8 = '1'
$env:BCC_ENVIRONMENT = 'demo'
$env:BCC_DATABASE_URL = 'postgresql+asyncpg://bcc:bcc@127.0.0.1:55432/bcc_performance_20261120'
$env:BCC_REDIS_URL = 'redis://127.0.0.1:56379/0'
$env:BCC_REQUEST_RATE_LIMIT_PER_MINUTE = '10000'
uv run --no-sync uvicorn app.main:app --host 127.0.0.1 --port 8765 --no-access-log
# Следующие команды — в другом терминале, после /ready:
uv run --no-sync python -m scripts.benchmark_antifraud --redis-url redis://127.0.0.1:56379/2 --samples 500
uv run --no-sync python -m scripts.benchmark_http --base-url http://127.0.0.1:8765 --requests 500 --warmup 30 --concurrency 1 --accounts accounts.json
uv run --no-sync python -m scripts.benchmark_http --base-url http://127.0.0.1:8765 --requests 500 --warmup 30 --concurrency 8 --accounts accounts.json
```

`accounts.json` — массив 200 разных `{id, phone}` из фоновых счетов, исключая четыре
фиксированных demo account. Поддержаны UTF-8 и UTF-8 с BOM. Без файла используется
один отправитель, который может достигнуть защитной ёмкости 512 записей: ожидаемый
`503` тогда считается ошибкой измерения, а не успешной оценкой.

## Исторический результат 19 ноября

Предыдущая среда: Linux, Xeon 2,30 GHz / 4 ядра, Python 3.12.3, локальные PG 16.15 и
Redis 7.0.15. Engine p95 1,06 мс; HTTP p95 на 1000 запросах — 23,5 / 168,7 / 360,9 мс
при конкуренции 1 / 8 / 16. Это другая машина и предыдущая методика: прогрев и
throughput не были строго отделены, в процентили входили только успешные ответы.
В старом отчёте `synchronous_commit` не зафиксирован. Эти числа не заменяют текущие
замеры и не подтверждают ускорение или регрессию кода.
