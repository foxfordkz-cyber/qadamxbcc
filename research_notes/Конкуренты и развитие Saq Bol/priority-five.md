# Шесть приоритетных конкурентов: что подтверждает код

Проверено 20 ноября 2026 года. Область: `tihiy-kod`, `Qaqpan`, `transferguard-itu`, `dropradar`, `bcc-aman` и добавленный `Qorgan`. Это анализ публичного исходного кода на зафиксированных коммитах, не испытание чужой инфраструктуры. Чужой код не запускался; пользовательские данные не отправлялись. Скриншоты работающих приложений не получены. Доступность публичного deployment и соответствие deployment указанному SHA не подтверждены.

Первичные источники — GitHub API, страницы GitHub, raw-файлы на SHA. Для Qorgan после ограничения публичного API использован read-only `git ls-remote`, raw-файл и заголовок commit patch. У первых пяти репозиториев API вернул `license: null`, отдельного LICENSE в просмотренных деревьях не обнаружено. У закреплённого Qorgan состав дерева перепроверен по архиву GitHub. Среди его файлов нет отдельного LICENSE. Это не разрешение на перенос кода или изображений: ниже предложены самостоятельные изменения нашего продукта.

## 1. «Тихий код»: какие обходы закрыты серверной логикой?

**Вывод.** Наиболее полезный для нас пример контекстной защиты между несколькими попытками. Это явно rules engine, не ML. Сильная сторона — последовательность действий клиента, а не число интерфейсных экранов.

**Версия:** [82b9cbfa, 19.11.2026 17:25 UTC](https://github.com/narutouciha431-sketch/tihiy-kod/commit/82b9cbfa4ddae759d72981942beab11c865b42cd).

**Подтверждено кодом.** `RiskInput` использует сумму переводов тому же получателю за окно, наличие незавершённого удержания, вставку реквизитов, паузы ввода и переключения приложения. Паузы сравниваются с персональным baseline; активное удержание плюс новый получатель дают красный результат. Существуют отдельные условия «кредит во время звонка» и явно отмеченный получатель. [risk.py, строки 25–112](https://github.com/narutouciha431-sketch/tihiy-kod/blob/82b9cbfa4ddae759d72981942beab11c865b42cd/server/risk.py#L25).

История берётся из SQLite: `window_sum` исключает черновики/отмены; `has_pending` ищет незавершённые переводы отправителя. Флаги делятся на временные и подтверждённые. [db.py, 205–235](https://github.com/narutouciha431-sketch/tihiy-kod/blob/82b9cbfa4ddae759d72981942beab11c865b42cd/server/db.py#L205). При удержании создаётся предварительный флаг получателя; после завершения звонка клиент получает дополнительную проверку. Разрешение доверенного лица не перекрывает тихий сигнал клиента. [main.py, 68–129](https://github.com/narutouciha431-sketch/tihiy-kod/blob/82b9cbfa4ddae759d72981942beab11c865b42cd/server/main.py#L68), [таймер, 155–164](https://github.com/narutouciha431-sketch/tihiy-kod/blob/82b9cbfa4ddae759d72981942beab11c865b42cd/server/main.py#L155).

**Доказательство качества, с ограничением.** Опубликован воспроизводимый синтетический стенд: 45 мошеннических и 40 обычных сценариев; авторы сообщают 39 задержанных мошеннических, 5 ложных пауз, отдельно показывают влияние веса звонка. Сами прямо отказываются считать это банковской точностью. Стенд включает честную оплату продавцу во время разговора, медленный привычный ввод и дробление суммы. Эти опубликованные результаты здесь не воспроизводились. [Результаты стенда](https://github.com/narutouciha431-sketch/tihiy-kod/blob/82b9cbfa4ddae759d72981942beab11c865b42cd/docs/test-stand-results.md).

**Ограничения по коду.** Состояние операции, баланс и журнал меняются отдельными вызовами; `_exec` коммитит каждый SQL statement. Поэтому запись всей финансовой операции атомарно не следует из просмотренной реализации. PIN/тихий код представлены полями SQLite; это не production IAM. Наличие Python RLock не доказывает межпроцессную корректность. [db.py, 15–18](https://github.com/narutouciha431-sketch/tihiy-kod/blob/82b9cbfa4ddae759d72981942beab11c865b42cd/server/db.py#L15), [147–151](https://github.com/narutouciha431-sketch/tihiy-kod/blob/82b9cbfa4ddae759d72981942beab11c865b42cd/server/db.py#L147), [confirm, 444–470](https://github.com/narutouciha431-sketch/tihiy-kod/blob/82b9cbfa4ddae759d72981942beab11c865b42cd/server/main.py#L444).

**Сравнение с Saq Bol.** У нас сильнее проверяемая транзакционная история, Postgres-конкуренция, идемпотентность, отдельные settlement/attempt и подтверждённый SOC-флаг. При этом смена получателя после удержания заслуживает отдельной проверки: нельзя позволять обнулить серверный контекст выключением переключателя «звонок». Переносить их жёсткий красный порог не следует: безопаснее ограниченная дополнительная проверка нового получателя в исходном окне удержания.

## 2. Qaqpan: как объяснить родственнику риск и выйти за рамки одного перевода?

**Вывод.** Сильный связный сценарий «сообщение → звонок → перевод → помощь семьи», понятный неспециалисту. Серверная логика есть, но состояние остаётся демонстрационным.

**Версия:** [5fa87067, 20.11.2026 07:10 UTC](https://github.com/adiletpn/Qaqpan/commit/5fa87067bf89eed5bcff770b3587370af506d57c).

**Подтверждено кодом.** Rules scoring выделяет перевод на собственный счёт в другом банке во время звонка; знакомый получатель снижает риск только вне звонка. Это полезная защита от слишком сильного признака «свой/знакомый». Есть вставка и переключения приложения. [risk.py](https://github.com/adiletpn/Qaqpan/blob/5fa87067bf89eed5bcff770b3587370af506d57c/api/risk.py).

Карточка для родственника объясняет конкретную сумму, долю баланса, звонок, получателя и ответы клиента. История содержит только известные приложению события, не заявляет чтение всех SMS/разговоров. Выключение семейной защиты откладывается на сутки с уведомлением; отсутствие ответа за 15 минут передаёт вопрос сотруднику. [family.py, 1–8, 29–89, 116–138](https://github.com/adiletpn/Qaqpan/blob/5fa87067bf89eed5bcff770b3587370af506d57c/api/family.py).

Сервер под `STATE.lock` сохраняет решение и меняет демонстрационный баланс; семейная проверка применяется к операции даже при ответах «нет». Для публичного режиссёрского API есть опциональный ключ ведущего. Однако идентификация клиента в просмотренных маршрутах — переданный ID; production-авторизация банковского клиента из этого не следует. [main.py, 42–59](https://github.com/adiletpn/Qaqpan/blob/5fa87067bf89eed5bcff770b3587370af506d57c/api/main.py#L42), [300–345](https://github.com/adiletpn/Qaqpan/blob/5fa87067bf89eed5bcff770b3587370af506d57c/api/main.py#L300). README честно описывает память одного процесса и дальнейшую банковскую интеграцию. [README](https://github.com/adiletpn/Qaqpan/blob/5fa87067bf89eed5bcff770b3587370af506d57c/README.md).

**Метрики.** Авторы публикуют проверку 47 сообщений, из которых 29 мошеннические и 18 обычные; часть взята из новостей, большинство сконструировано. Они раскрывают доработку промпта на том же наборе и оптимистичность цифр. Это важнее красивого процента: эти цифры нельзя сопоставлять с нашей оценкой переводов или считать независимым holdout. [METRICS.md](https://github.com/adiletpn/Qaqpan/blob/5fa87067bf89eed5bcff770b3587370af506d57c/docs/METRICS.md).

**Сравнение с Saq Bol.** Нам полезна единая короткая история доказательств для клиента/SOC/доверенного лица. У нас уже есть банковская проверка звонка, duress, advisory trusted contact и кейсы; не нужно вводить LLM в горячий путь или обещать, что совет родственника переводит деньги. «Свой счёт в другом банке» потребует реального банковского ownership-сигнала, которого в нашем текущем API нет: не подменять его переключателем пользователя.

## 3. TransferGuard: как отделить недостаток данных от высокого риска?

**Вывод.** Небольшой, аккуратно ограниченный прототип: отдельное состояние «нужны ответы» и ясная рекомендация до подтверждения. Сравнивать его с полноценным SOC backend некорректно.

**Версия:** [c8da1f67, 19.11.2026 12:21 UTC](https://github.com/your-golden-hour/transferguard-itu/commit/c8da1f67eafc9de0cf8067a08139bd5b72c98092).

**Подтверждено кодом.** Пять правил, ответы `true/false/null`, список недостающего контекста, отдельные действия ASK_CONTEXT / REVIEW_DETAILS / STOP_AND_VERIFY_WITH_BANK. Ответ маркируется `rules-v0.1` и `isDemo: true`. [risk.ts](https://github.com/your-golden-hour/transferguard-itu/blob/c8da1f67eafc9de0cf8067a08139bd5b72c98092/lib/risk.ts). API валидирует строгую Zod-схему, положительную целую сумму, JSON Content-Type и лимит тела 2048 байт. [route.ts](https://github.com/your-golden-hour/transferguard-itu/blob/c8da1f67eafc9de0cf8067a08139bd5b72c98092/app/api/risk/evaluate/route.ts).

UI ждёт серверную оценку и показывает ошибку при сбое. Есть Node tests граничной суммы/ошибочных payload и Playwright-файл; тесты здесь не запускались. [page.tsx, 43–62](https://github.com/your-golden-hour/transferguard-itu/blob/c8da1f67eafc9de0cf8067a08139bd5b72c98092/app/page.tsx#L43), [risk.test.ts](https://github.com/your-golden-hour/transferguard-itu/blob/c8da1f67eafc9de0cf8067a08139bd5b72c98092/tests/risk.test.ts), [demo.spec.ts](https://github.com/your-golden-hour/transferguard-itu/blob/c8da1f67eafc9de0cf8067a08139bd5b72c98092/e2e/demo.spec.ts). README называет операции вымышленными; в просмотренном дереве нет финансового ledger, графового сервиса или ML training. [README](https://github.com/your-golden-hour/transferguard-itu/blob/c8da1f67eafc9de0cf8067a08139bd5b72c98092/README.md).

**Сравнение с Saq Bol.** Полезная UX-идея — объяснять, каких данных не хватает, вместо превращения неизвестного в «безопасно». Наши неизвестный исход запроса, недоступный backend и пропавший кейс уже требуют самостоятельных состояний восстановления. Их не следует смешивать со score 0. Для нас приоритет — сделать эту честность заметной, сохранив существующие контракты.

## 4. DropRadar: есть ли настоящее ML и как показывается adversarial сценарий?

**Вывод.** Реальный browser inference сериализованного ансамбля плюс выразительная песочница атак. Однако опубликованные показатели качества не воспроизводимы по доступному репозиторию.

**Версия:** [1bc435ad, 19.11.2026 18:50 UTC](https://github.com/aikenmurat1-design/dropradar/commit/1bc435ad050d7f7d05ce3e49f1bba8b7e2230fb6). В дереве один файл с буквальным именем `index.html.`.

**Подтверждено кодом.** Встроены два набора деревьев и feature names; `predict` проходит массивы split/leaf и применяет sigmoid. Это больше, чем статическая надпись «AI». Признаки включают fan-in, транзит, время удержания, направления вывода, возраст/зарплату/бизнес; v2 добавляет долю отправителей с необычным поведением. [index.html., 285–291](https://github.com/aikenmurat1-design/dropradar/blob/1bc435ad050d7f7d05ce3e49f1bba8b7e2230fb6/index.html.#L285).

Основной сценарный replay использует сохранённый `e.score`; отдельный `runAttack` генерирует поток по параметрам жертв/интервалов/дробления/направления и пересчитывает признаки. Не следует выдавать оба режима за одинаковый live scoring. [341–350](https://github.com/aikenmurat1-design/dropradar/blob/1bc435ad050d7f7d05ce3e49f1bba8b7e2230fb6/index.html.#L341), [439–480](https://github.com/aikenmurat1-design/dropradar/blob/1bc435ad050d7f7d05ce3e49f1bba8b7e2230fb6/index.html.#L439).

SOC показывает ложные тревоги наряду с дропами и составляет черновик сообщения. Нажатие «заморозить/отпустить» меняет клиентское состояние/текст; показанная фраза про учёт моделью не подтверждается обучением в этом обработчике. [544–560](https://github.com/aikenmurat1-design/dropradar/blob/1bc435ad050d7f7d05ce3e49f1bba8b7e2230fb6/index.html.#L544).

**Граница доказательства.** Метрики, размеры тестовых выборок, утверждения о невиданных кольцах и importance встроены в JSON. Упомянутого генератора и training/evaluation scripts в дереве нет. Проверена структура данных, не независимая истинность цифр. Нельзя сравнивать их recall с нашим p95 или объявлять победителя по таким значениям. Цвета/компоновка из CSS указывают тёмный аналитический интерфейс, а не нужную нам светлую BCC-систему.

**Сравнение с Saq Bol.** Наша сильная сторона — воспроизводимые trainer/evaluation, backend graph и durable действия. У нас уже есть `evaluate_fraud_model.py`, ablation и сценарная панель; делать второй стенд ради галочки не нужно. Полезное дополнение — сценарий обхода и парный честный контроль, прогоняемые через настоящий API, с раздельным показом задержанных денег, окончательно заблокированных переводов и ложных тревог.

## 5. BCC Аман: что даёт семейная история в трёх ролях?

**Вывод.** Сильный демонстрационный рассказ: клиент, родственник, банковский сотрудник одновременно видят последствия. Финансовая и биометрическая части — браузерная симуляция.

**Версия:** [ed4ca472, 19.11.2026 17:18 UTC](https://github.com/aikenmurat1-design/bcc-aman/commit/ed4ca472e8efc5c57af06d3f906f5dcfafa83537). Дерево: README и `index.html`.

**Подтверждено кодом.** Rules учитывают обычную сумму, нового получателя, звонок, колебания, число/сумму отправленных операций, fan-in и дальнейший вывод. Но «24 часа» в UI не подтверждены фильтром времени: агрегируется весь клиентский `S.ledger` текущей сессии. [184–200](https://github.com/aikenmurat1-design/bcc-aman/blob/ed4ca472e8efc5c57af06d3f906f5dcfafa83537/index.html#L184).

Удержание показывает два телефона, запрос родственнику и десятиминутный countdown. «Проверка лица» для больших сумм — `setTimeout` на 1,3 секунды; одобрение изменяет JS-баланс/ledger. Это не биометрическая верификация и не серверное движение денег. [217–245](https://github.com/aikenmurat1-design/bcc-aman/blob/ed4ca472e8efc5c57af06d3f906f5dcfafa83537/index.html#L217). В доступном дереве нет backend, training или test suite. По CSS — тёмная зелёно-золотая банковская стилизация, не доказательство официального дизайна BCC.

**Сравнение с Saq Bol.** Можно улучшить совместную историю действий, используя наши существующие кейсы/журнал/контакт. Нельзя обещать распознавание лица на основании анимации или давать родственнику несуществующее полномочие разблокировать банковский перевод. Для нас важнее видимое подтверждение реального server-side изменения, чем четвёртый демонстрационный экран.

## Что улучшать у нас в первую очередь

**P0 — ограниченная защита от смены получателя после удержания.** Проверять в SQL недавнее незавершённое cooling-off того же отправителя; если новый перевод идёт другому незнакомому получателю, требовать дополнительную проверку даже после очистки браузерных флагов. Не hard block, не перенос обвинения на получателя, не бесконечное продление удержаний. Привязать срок к исходному окну, не считать дочерние проверки новой первопричиной. Нужны тесты смены получателя/worker/restart, чистого знакомого получателя, истечения/отмены исходного удержания, конкурентных запросов и повторного request_id. Основание: обход, явно закрытый в «Тихом коде», а не его произвольный вес 0,95.

**P1 — сделать доказательства решения удобными для человека.** Согласованная RU/KK история: какой сигнал серверный, какой браузерный, что изменилось, почему ждём, что разрешено дальше. При недоступности/неизвестном исходе — состояние восстановления; ML-процент не называть достоверной вероятностью мошенничества на данных банка. Для новых действий сохранять existing request_id/version и подтверждать результат сервером. Основание: ясность семейной карточки Qaqpan и разделение неизвестного контекста TransferGuard.

**P1 — дополнить существующую оценку парными сценариями обхода и честного поведения.** Использовать уже имеющийся `backend/scripts/evaluate_fraud_model.py`, не создавать дублирующий benchmark. Отдельно показывать same-generator synthetic evaluation, вручную составленные adversarial сценарии и отсутствие реального банковского holdout. В демонстрации показать не только остановленный дроп, но и честный fan-in/знакомый перевод, который проходит. Основание: честная чувствительность/false-positive отчётность «Тихого кода», раскрытие утечки настройки Qaqpan, интерактивная атака DropRadar. Это усилит доказательство, не создавая выдуманный рейтинг точности.
